Closing the Gap

  • There's a pretty large gap between advanced agentic coding patterns and basic prompting of tools like Claude Code
  • This talk is going to cover the basics, and it'll be things many of you already know, but I want to make sure we are all operating from a common ground
  • Transition: So what's the gap?
Prompt Engineering → Context Engineering
  • Agentic coding has moved from prompt engineering as a focus to context engineering
  • Which means that rather than optimising the text we give the LLM in any given prompt, we're optimising the systems that the LLM is operating in
  • Because forefront models have gotten really good at understanding intent, even with sloppy prompts. But they all operate within a fundamental constraint, their context windows
  • Transition: So what's context anyway?

  • To get definitions out of the way, the context window is the LLMs current working memory
  • Basically, everything that has happened in the current session (instructions, conversation, files read, tool uses) along with whatever system prompts it has
  • That window has real constraints that degrade results if you ignore them

Death by a thousand tokens

How context windows fail

Size

There's a hard limit we can't hit

Focus

vs

Irrelevant context dilutes the good stuff.

Rot

Long sessions degrade early context.

  • We broadly have a few fundamental limitations in LLM context — size, focus, and rot
  • Size: Context windows have a fixed size. This varies by model, and Anthropic are currently experimenting with vastly larger windows than we currently have access to
  • When that window gets full, you need to kill the session. Most harnesses have a feature called compaction, which basically automates this by creating a little "handover summary" to the next agent of everything that went into the context window of your dead session. That used to be a black box, but most harnesses now let you invoke it manually, scope what gets kept, or hand off to a fresh session deliberately. Treat auto-compaction as a last resort, not a feature — by the time it kicks in, the session has usually already rotted
  • Focus: Even if you had an unlimited context window, LLMs still benefit from being focussed, just like human engineers do. If you throw a dozen completely unrelated issues or tasks at an agent within one session it's going to get awfully confused sooner or later
  • Rot: The mitigation to that problem creates another one — context degradation. The longer a session goes on and the more a context window fills with noise, the model's attention to earlier instructions tends to degrade as it tethers to the more recent context
  • Transition: So let's talk about the tools we have at our disposal to mitigate these constraints

Instructions

AGENTS.md

Providing a baseline

  • The first tool we have at our disposal is system instructions — a markdown file at the project root that most harnesses load automatically. AGENTS.md is the emerging cross-tool convention; Claude Code calls it CLAUDE.md, Cursor has its own rules format, but they all do the same job
  • This is loaded into the context window at the start of every single session
  • It's one and only goal is to save time (ie: context) by telling the agent things it needs to know very often, without it having to go searching to figure it out repeatedly
  • Transition: Since this is in every single session, every line must earn its place

Earn every line

  • The key principle here is that your instructions are the place to tell the agent all the gotchas about your specific project it needs to know about
  • It is not the place to tell the agent to be a good boy and write really nice code
  • It is not the place to document every facet of your entire architecture
  • It is not the place to summarise all the files in your project

On-demand context with skills

  • The next primitive we have at our disposal are skills
  • You can think of skills as a progressive disclosure mechanism
  • Whereas AGENTS.md is the baseline for every agent in every session, skills are discovered and read by agents as they need them
  • If something should be known every session, like what testing commands should be run, it belongs in AGENTS.md. If something only relates to part of your codebase or certain tasks, like our opinionated service architecture patterns for an internal API, it belongs in a skill
  • Transition: So how do we write a skill?

  • The easy answer is ask the agent to do it — most harnesses ship a skill-writing skill that's pretty great. But let's cover the principles too
  • Concise: Context window is a shared resource — only add what the agent doesn't already know
  • Pushy description: Agents under-trigger skills by default — be explicit about when to use them
  • Progressive disclosure: Point to detail docs rather than inlining everything. The agent reads files on demand.

Don't write skills for things the model is already great at

✗ Skill stuffing

writing-typescript
running-tests
git-commit-best-practices

✓ Load-bearing

our-weird-internal-rpc
deploy-to-staging-cluster
cutting-a-release
the-event-bus-pattern
running-a-migration
  • Before we look at the anti-pattern: useful skills generally fall into two shapes. Reference skills capture facts about your world — your internal RPC pattern, the staging cluster's quirks, the reason your event bus is shaped weirdly. Recipe skills capture procedures — adding an endpoint, cutting a release, running a migration. Both are valid.
  • The principle from AGENTS.md applies just as hard to skills: don't fill the context window with things the model already knows
  • The first failure mode teams hit after discovering skills is to write skills for everything. A writing-typescript skill. A running-tests skill. A git-commit-best-practices skill. These are worse than useless — they consume context to tell the model things it's better at than you are
  • A useful skill compresses something load-bearing about your world. Things the model couldn't possibly know without you telling it
  • A good gut check: if the skill's contents would be reasonable to put in a public blog post, it probably shouldn't be a skill. If it'd get you fired for posting it, that's a skill
  • Same principle, different surface — earn every line, earn every skill

Tools

Mind the tool tax

What the agent can do

TOOLS ATTACHED
bash read edit grep glob write mcp:linear mcp:slack mcp:notion webfetch
~12k tokens · every turn
  • Tools are the verbs available to the agent — read a file, run a shell command, hit an API. Every harness ships a default set out of the box
  • You can extend that set in a few ways. The most common right now is MCP — Model Context Protocol — Anthropic's standard for exposing third-party services as tools. Linear, Notion, Slack, your internal data warehouse — anything with an MCP server can be plugged into your agent
  • The catch: every tool the agent could reach for sits in its system prompt as a description, every turn. Whether the agent uses it or not, you're paying for it. A team that attaches a dozen MCP servers can quietly burn fifteen thousand tokens of context before a session even starts
  • This is why MCP has been getting a more cautious reception lately. The industry has been quietly rediscovering that bash is already a universal protocol. Agents are excellent at driving gh, psql, kubectl, aws directly. MCP earns its keep for stateful, auth-heavy surfaces — for everything else, the CLI is right there
  • Modern harnesses are responding with auto-discovery and lazy tool loading — a tool's schema only materialises when the agent actually wants to call it. A context-engineering response to a context-engineering problem
  • Transition: So we've covered what the agent knows and what it can do. What about how it splits work?
Subagents
"The Testing Expert™" "The Architecture Specialist™"
Focused context for a focused task.
  • The temptation with subagents is to think of them as personas — "you are the testing expert, you are the architecture guru." That's cargo-culting. The model doesn't become better at testing because you told it it's a specialist.
  • This is also where harnesses diverge the most in their implementations. Claude Code handles subagent delegation implicitly — the agent decides when to spawn a subagent on its own. Something like opencode exposes it as a user-facing primitive you control directly. Same concept, very different ergonomics.
  • What actually makes a subagent useful is context isolation. A subagent gets a fresh, focused context window dedicated to a single concern. That's the value — not the role-play.
  • This is the same principle we've been talking about all along — focus. Except now instead of curating what goes into one context window, we're splitting work across multiple windows.
  • Transition: Once you see subagents as context- shapers, you can spend that isolation in two different ways.

Workers and scouts

Two modes, same primitive

Workers

"Go do this thing. Come back when it's done."

Isolation spent on execution.

Scouts

"Go find out X. Come back with 200 words."

Isolation spent on compression.

  • Once people get the idea of subagents, they tend to reach for them in one way — delegation. "Go build this feature in your own context window." That's a valid use, and it's what most of the agent-team patterns we'll see later are built on
  • But the more underused mode is scouting. You spin up a subagent not to do work but to find out something. Read fifty files. Map the call graph. Investigate a weird bug. Come back with a tight summary
  • The reason this matters: a scout is a context filter. The investigation might touch fifty files; what lands in the parent's context is a 200-word report. You've turned an expensive read into a cheap summary
  • This is the move that quietly underwrites adversarial review later. A reviewer is structurally a scout — it goes off, looks at a thing with fresh eyes, reports back. Once you internalise the scout pattern, review stops feeling like a special case
  • Both modes are buying the same thing — isolation. They just spend it differently. Workers spend it on doing. Scouts spend it on seeing

Context isolation in practice

One task, too many concerns for one context
↓ split by concern
Agent A
Only sees implementation
Agent B
Only sees documentation
Agent C
Only sees code review
Each agent has a discrete piece of work with a full context window to dedicate to it
  • Here's what context isolation looks like in practice. You've got one task that touches too many concerns for a single context window to handle well — implementation, docs, review.
  • Instead of stuffing all of that into one session where the agent is juggling everything at once, you split by concern. Each subagent only sees what it needs to do its job.
  • Agent A doesn't know about the docs. Agent B doesn't know about the implementation details. That's a feature, not a bug — it means each one gets a full, clean context window dedicated entirely to its piece.
  • This is basically the single-responsibility principle, but for context windows instead of classes.

Patterns

How does it all fit together?

  • So we've covered the three building blocks — AGENTS.md for the baseline, skills for on-demand context, and subagents for context isolation.
  • Each of those is useful on its own, but the real leverage comes from how you compose them together into repeatable patterns.
  • We're going to look at three: spec-driven autonomous loops, agent teams, and adversarial review.

Spec-driven & autonomous coding

Spec
→
Agent
→
Run
→
Check
→
Fix
↻
  • This slide is really two ideas that reinforce each other — spec-driven development, and autonomous loops.
  • Spec-driven is the more fundamental one. Even without full autonomy, externalising your intent into a spec file pays off immediately. Plan-mode features in most harnesses are a form of this — you write a plan together, it saves it to a file, then spins up a fresh agent that picks up that plan as external context. Clean window, clear intent. LLMs don't have cross-session memory, so the spec becomes the thing that carries intent, decisions, and constraints across sessions.
  • The autonomous loop layers on top of that. Each iteration is a totally fresh session — the agent implements, checks, updates the spec with what it did, and exits. The next agent boots into a clean context, reads the updated spec, and picks up where the last one left off. That's how you avoid rot — you're never in one session long enough for it to degrade.
  • The "check" step is critical — tests, type-checking, linting. Without that feedback loop it's just vibes.
  • When this pattern works well, you can genuinely kick it off and go make a coffee. When it doesn't, it's almost always because the spec was underspecified or there was no automated check to keep it honest.

Implementation
source files

test files

documentation
  • This is the natural extension — instead of one agent looping through a spec, you fan out multiple agents working in parallel, each responsible for a different concern.
  • They all read the same spec, so they share the same understanding of what needs to happen. But each one only loads the files relevant to its job. Implementation doesn't see test files. Tests don't see docs. Focused context, in parallel.
  • The spec is one coordination mechanism, but agents working in parallel also need to avoid stepping on each other's work. Different harnesses take very different approaches here. Claude Code's agent teams use a shared task list with file-level locks so two teammates can't claim the same work, plus inbox-based messaging between agents and isolated git worktrees per agent to prevent file conflicts. Kimi's agent swarm takes the opposite approach — a trained orchestrator that decomposes a task and dynamically spawns sub-agents to run in parallel, coordinating them centrally rather than having peers negotiate. One is bottom-up coordination between equals, the other is top-down orchestration. Both experimental, both tackling the same fundamental problem from very different angles.
  • Fair warning though: this is all bleeding edge. Coordinating agents that write to the same codebase introduces real challenges — merge conflicts, race conditions, agents stepping on each other's work. Powerful, but not free.

Let's fight

Adversarial review & backpressure

Builder's context

Full of the journey — false starts, back-and-forth, accumulated assumptions

→

Reviewer's context

Sees only the output. Catches what the builder can't.

  • This is one of the most underrated patterns. After an agent builds something, its context is full of the journey — false starts, dead ends, accumulated assumptions. It's lost objectivity on its own output.
  • So you spin up a fresh agent with a clean context whose only job is to review what the builder produced. It has no baggage, no sunk cost. It sees the code the way a colleague on your team would see it in a PR.
  • This is backpressure — the reviewer pushes back on the builder. And because the reviewer's context isn't polluted with the builder's reasoning, it catches things the builder literally can't see anymore.
  • You can wire this into an autonomous loop too — build, review, fix, repeat. The tension between the two contexts is what produces the quality.

  • We've covered three patterns as if they're standalone things — spec loops, agent teams, adversarial review. They're not. They compose, and the real leverage shows up when you stack them
  • You could spec-drive a team. You could wire adversarial review into a loop as the check step. You could put a scout subagent inside a forked skill. None of these primitives or patterns are jealous of each other
  • The meta-pattern is this: every pattern in this talk is a way of taking something the talk's already covered — a context window, a primitive — and spending it differently. Once you internalise that, you stop reaching for "the right pattern" and start asking "what context does this work actually need, and how do I shape it?"
  • A good prompt when you're stuck: what's the smallest context window that could do this job? And what's the smallest one that could check it? The answer is often a combination nobody's written down anywhere
  • The team in the room Monday morning will invent combinations I haven't thought of. That's the point — these are ingredients, not recipes
